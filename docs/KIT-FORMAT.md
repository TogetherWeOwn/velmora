## Kit contents and trust model

A kit contains `manifest.json`, `index.vki`, `records/records-NNN.tar.zst`, `KIT-FORMAT.md`, and the recovery tool binaries and source. `manifest.json` is plaintext metadata: format version, kit ID, build timestamp, source listing counts, file SHA-256 and byte counts, and tool version. It must not contain object keys, bucket names, article IDs, or keys. A file hash detects accidental mismatches; it is not a substitute for verifying the index and record AEAD tags. Use a trustworthy copy of the tool and the separately held KEK. The kit neither includes the KEK nor changes cache eviction.

Each pack is a zstd-compressed USTAR archive of regular files with unique paths. The zstd window is at most 8,388,608 bytes; the expanded archive is at most 8 GiB and each member is at most 64 MiB. GNU/PAX extension headers, sparse records and links are not part of format 1. The tar path is the original, byte-exact record name starting `m/`, without the remote archive prefix or a leading slash. The file body is the stored sealed record, byte-for-byte. Treat pack paths as data: reject traversal, absolute paths, and links; a reader need not extract any pack onto disk. All eligible `m/` records including superseded records are packed; exclude tenant keys (`m/tk/`, including under a tenant root) and non-`m/` namespaces such as `rs/`. Auxiliary families not used for object recovery are opaque, not live entries.

## Sealed catalogue records

Recovery records can have a **flat** root `m/` or a **tenant** root `m/x/<tenant>/`. In both layouts append the following suffixes to the root. Do not change the root, strip it, change case, or normalize a name for cryptographic operations.

| Suffix | Plaintext UTF-8 JSON |
|---|---|
| `g_<id suffix>` | Version 1: `{v:1,bucket,generation,extents}`. Version 2: `{v:2,bucket,generation,set,segments}`. |
| `seg/<set>/<index>` | Version 2: `{v:2,set,index,extents}`; `index` in the name is zero-based decimal padded to five digits. |
| `del/g_<id suffix>` | `{v:1,id,bucket_id,key,deleted_at}`. |
| `art/<extent_id>` | `{v:1,extent_id,plan_rev,articles,packed?,parity?}`. |

A record is `kek_version:u32be || 0x01 || nonce[24] || ciphertext || tag[16]`. The record key is HKDF-SHA256 with no salt, the 32-byte KEK as IKM, ASCII info `velmora/manifest/v1`, and 32-byte output. Open with XChaCha20-Poly1305 and AAD `velmora/manifest/v1|<full record name>|<kek_version>` (UTF-8, decimal version without padding). Use the named KEK version, not a fallback. Authenticate before parsing. A plain record's identity must agree with the name. Binary JSON fields are standard padded base64.

- `bucket`: `id`, `name`, `owner`, `bdk_wrapped` (binary), `kek_version`, `disposable`, `created_at`.
- `generation`: `id`, `key`, `size`, `etag`, `checksum_json` (string or null), `content_json`, `user_meta_json`, `created_at`. Fields ending `_json` are JSON encoded as strings.
- `extent`: `id`, `seq`, `plain_offset`, `plain_size`, `cipher_size`, `media_header` (48 bytes), `key_mode`, `wrapped_file_key` (73 bytes), `plain_md5` (16 bytes), `plain_sha256` (32 bytes), `cipher_sha256` (32 bytes), `created_at`. Offsets and sequence belong to the ordered generation placement. Sizes are bytes.
- Version 2 `segments` entries: `seq`, `count`, `plain_offset`, `plain_size`, `sha256` (32 bytes). Use the head's layout and set to find each segment. Compare its **sealed** bytes' SHA-256, then verify the AEAD and check set, index, extent count, sequence and plaintext span. Missing or mismatched segments make the generation unreadable, not an empty object.
- `articles` contains the explicit data rows in zero-based `idx` order: `idx`, `message_id`, `newsgroup`, `headers` (binary), `cipher_offset`, `cipher_len`, `payload_sha256` (32 bytes), and optional `yenc_name`. `packed` and `parity` are binary. A packed data plan never replaces the explicit rows for recovery. The native codec in `crates/velmora-bridge/src/parity.rs` validates and expands parity; see below.

Compute the replay-live state for each `(bucket.id, generation.key)` by selecting the lexicographically highest generation or tombstone ID across both layouts. A winning tombstone suppresses the object. A generation ID is `g_` plus 13 lowercase hexadecimal digits of mint milliseconds and 16 lowercase random hex digits. Do not order by the remote key, last modified time, JSON timestamp, or pack order. This is replay-live state, not evidence that a particular publication was acknowledged; the sealed record can precede its catalogue commit. Superseded generations remain in the packs.

## Key chain and media

Wrapped keys are `0x01 || nonce[24] || ciphertext[32] || tag[16]` using XChaCha20-Poly1305. The BDK is wrapped by the 32-byte KEK identified by the bucket's `kek_version`; its AAD is `velmora/bdk/v1|<bucket id>|<kek_version>`. The file key is wrapped by the BDK; its AAD is `velmora/fk/v1|<bucket id>|<extent id>`. Use the exact UTF-8 strings, decimal numbers and literal `|` separators. No plaintext key belongs in the kit or any intermediate file.

`velmora.media.v1` ciphertext starts with the 48-byte `N[16] || commitment[32]` header. This must match the authenticated record's media header. For the S3 profile the key mode is `0x01` (random), context `velmora-s3/media`. With the file key as IKM and `N` as salt, derive the commitment by HKDF-SHA256 to 32 bytes with info `velmora.media.v1/commit || 0x00 || 0x01 || velmora-s3/media`; compare it before attempting chunk decryption. Derive the payload key from the same extract, 32 bytes with info `payload`. Each chunk is at most 65,536 plaintext bytes plus a 16-byte ChaCha20-Poly1305 tag. Chunk nonce is the zero-based counter as 11 big-endian bytes followed by a last-chunk byte (0 or 1); chunk AAD is empty. The trusted plaintext size determines `L = max(1, ceil(plain_size / 65536))` and the expected ciphertext size `48 + plain_size + 16*L`. Even an empty media stream has a final authenticated chunk. Verify the entire extent's ciphertext SHA-256, then the plaintext SHA-256 and MD5. Do not publish a file before all of its extents and the applicable whole-object digest have been verified.

## Articles and NZB export

An article carries 11 full ciphertext chunks at most. The first article's maximum payload is 721,120 bytes (includes the 48-byte header); subsequent articles span up to 721,072 bytes. Cut consecutively at these lengths, truncating at the extent's ciphertext size. SHA-256 is over the raw decoded article payload, not the wire bytes. Match recorded explicit offsets and sizes to these cuts. Remove NNTP dot-stuffing if the transport has not already done so, decode yEnc by undoing `=` escapes (subtract 64 modulo 256) then subtracting 42 modulo 256; metadata and CRLF framing are not payload. Expected wrapper is `=ybegin` / optional `=ypart` / `=yend`; verify range and CRC when present, then the authenticated SHA-256. The legacy multipart yEnc representation and current standalone representation have the same ciphertext hash convention.

Parity recovery, where present, uses the stored addendum rather than regenerating policy: `tag=1:u8 || kind=0:u8 || parity_rev:u16be || k:u16be || shard_len:u32be || seed[16] || planned_secs:i64be || check[16] || groups || m:u8 || m*(row:u16be || sha256[32])`. Groups begin with a count byte; each group is one length byte then UTF-8 name bytes. The addendum is bound to the extent and its data plan; validate and materialize its rows using the versioned `parity.rs` codec beside `plan.rs`. If the addendum does not validate against the exported explicit rows, omit parity and count the omission without dropping the data plan. The extent's consecutive article payloads are the data shards, zero-padded to `shard_len`. Verify each fetched shard, reconstruct missing shards using the recorded rows and stored geometry, trim to the expected cuts, and check the recovered data payload digests.

NZBs are generated on demand, not a substitute for the kit. Use standard NZB XML escaping and the recorded groups. Use one `<file>` with one `<segment number="1">` for each standalone article; use a multipart file per extent for legacy articles without a `yenc_name`. Do not use bucket names or object keys in article subjects or filenames; do not provide plaintext objects to an NZB downloader. Use message IDs without the protocol's surrounding angle brackets as segment text. The kit's decrypt step uses the stored article sequence and authenticated hashes, not directory iteration order.

## Sealed index and deltas

The index starts with ASCII `VKI1`, followed immediately by frames. A frame is `flags:u8 || len:u32be || kek_version:u32be || 0x01 || nonce[24] || ciphertext || tag[16]`. `flags` is exactly 0 for nonfinal frames and 1 for the sole final frame; `len` counts bytes after itself (from `kek_version` through `tag`). Number frames starting at zero. Each frame encrypts exactly one complete zstd frame encoding up to 4,194,304 bytes of the uncompressed CBOR stream, using a zstd window of at most 4,194,304 bytes. Concatenate decoded slices before interpreting CBOR; a CBOR item may cross a frame boundary. Even an empty index has one final frame compressing the empty sequence. The final frame must be followed by EOF. The encoded `len` is at most 8,388,608 bytes, including its 45 bytes of envelope overhead but excluding `flags` and the length field. An index has at most 16,384 frames, at most 8,589,934,592 decoded bytes in total, and no CBOR item may exceed 16,777,216 bytes across one or more frames.

Each frame is sealed with XChaCha20-Poly1305 under HKDF-SHA256 (no salt, 32-byte KEK of the envelope version as IKM, 32-byte output) with the exact ASCII info `velmora/kit/v1`; use a fresh random 24-byte nonce. The AAD is exactly `velmora/kit/v1|<kit id>|<frame no>|<last 0/1>` in UTF-8, with decimal numeric fields without padding or sign and no version suffix. A kit ID is unique per build attempt and contains only ASCII alphanumerics, `-`, `_`. No KEK, BDK, file key, or plaintext index is written to disk. Authenticate every frame including the final frame, and verify EOF, before interpreting CBOR or exposing catalogue metadata. Wrong key, wrong identity, corruption, and truncation are errors.

The stream is a CBOR sequence (RFC 8742; no outer array). Each item is one definite-length text-keyed map with a `type` text discriminator. UTF-8 names and IDs are text; sizes, offsets and versions are unsigned integers; digests, header and wrapped keys are CBOR byte strings; lists preserve order. `plan_rev` and `checksum` must be present even when null; fields marked optional may be absent. Field names and types are:

- `bucket`: `id`, `name`, `bdk_wrapped` (73 bytes), `kek_version`.
- `object`: `bucket_id`, `key`, `generation_id`, `size`, `etag`, `content_type` (text or null), `headers` (all stored non-user content headers, a text-to-text map), `checksum` (stored checksum JSON as text, or null), `user_meta` (text-to-text map), optional `source_md5` (16 bytes), `extents` (ordered array of `{id, plain_offset, plain_size}`). Only these references carry placement. `source_md5` is an independent source digest, not a proof that the source's identity or bytes still match the stored object.
- `extent`: `id`, `bucket_id`, `plain_size`, `cipher_size`, `media_header` (48 bytes), `wrapped_file_key` (73 bytes), `plain_md5` (16 bytes), `plain_sha256` and `cipher_sha256` (32 bytes each), `plan_rev` (integer or null), `articles` (ordered array of `{message_id, newsgroup, payload_sha256, yenc_name?}`), optional `parity`, optional `verified`. A null `plan_rev` signifies an extent without a usable plan: `articles` is empty and `parity` absent. An object with such an extent is listed as not recoverable from Usenet yet. Parity is `{k, shard_len, rows}` with rows `{row, message_id, newsgroup, payload_sha256}`. Verified entries are `{backbone, kind, at}` with `at` an epoch-millisecond integer. A data plan records article locations before POST. Plan presence alone does not establish either posting success or release on any backbone. If the builder has only the records, `verified` is absent and catalogue release state is unknown.
- `record_ref`: `name` and `sha256` (32 bytes) of the original sealed record bytes. Match by exact name. Each included pack member has one reference.

Each kit is a self-contained full build. There are no deltas or predecessor metadata. `manifest.json` has `format_version:1`, `kit_id`, `built_at` (RFC 3339 UTC), `source_counts` (map of source to counts), `tool_version`, and `files` (array of `{path, bytes, sha256}`; digests are lowercase hex). The manifest's own SHA-256 is detached in `manifest.json.sha256`, not self-referential. The builder writes a single `sha256sum` text-mode line: 64 lowercase hex characters, two spaces, `manifest.json`, and LF. The recovery CLI also accepts the binary-mode separator (space then `*`) or a bare lowercase digest with no line ending, LF, or CRLF. Upload immutable files first and the manifest last; copy only completed builds. Retention targets seven daily and four distinct weekly copies; this format defines no remote deletion operation.

### Drill sample inputs

The local sampler requires JSON with an `objects` list and an `article_recorded_at` map. Each object row includes `bucket_name`, `key`, `size` in bytes, `md5` as 16 byte values, `source` (`run48-released` for already release-checked Usenet reads through 1 GiB inclusive, or `full-verify` for a completed whole-object Usenet read above 1 GiB), and `evidence_at`, the read time in UTC epoch milliseconds. The map associates exact article record names from the frozen source listing with their UTC epoch-millisecond recording time or a conservative upper bound (such as the mirror's LastModified). Match the object identity to the authenticated index and authenticate the relevant sealed records. Exclude the object unless its generation creation time and every selected plan's recording bound are known and not later than `evidence_at`. Historical evidence does not guarantee current provider availability. A sample copies the full index's exact selected extent plan revisions.

### Rust reader integration

`velmora_kit::read_index(reader: impl Read + Seek, kit_id: &str, kek: &impl velmora_bridge::ports::Kek) -> Result<Vec<velmora_kit::Entry>, velmora_kit::Error>` reads the sealed `index.vki`. `Entry` has struct-like variants `Bucket(Bucket)`, `Object(Object)`, `Extent(Extent)`, and `RecordRef(RecordRef)` (tuple variants wrapping named structs); the structs expose the fields above. Errors disclose no entry content. The complementary `write_index(writer, kit_id, kek, entries)` writes the framed sequence. `verify_packs(packs, &entries)` streams each zstd tar, verifies original names and bytes against the authenticated record references, and rejects missing, extra, duplicate, and non-regular members without extracting them. Verify outer pack sizes and SHA-256 against the manifest separately. The crate is native tooling only and is not linked into the deployed worker.
